# Reporter v2.1 Retrieval Evaluation Design

## Purpose

Make the v2.1 retrieval evaluation measure whether the application retrieves every expected statistical series over the expected period, and make missing evidence visible rather than allowing it to pass or disappear from the score.

This is the first step in the approved sequence to improve the v2.1 evaluation pipeline. It covers the execution contract scorer and its tests. Value scoring, KOSIS snapshot verification, and full-run gates will be handled in later steps.

## Current evidence

- The gold set has 200 cases: 140 `resolved`, 53 `no_match`, and 7 `need_clarification`; the resolved cases contain 294 series plans.
- 107 cases contain multiple series.
- The snapshot stores plans under `snapshot["series"]`, while the retrieval scorer currently looks up `snapshot[case_id]`.
- The current scorer compares the set of table IDs and uses combined rows for row count and period checks. It does not validate each fetched series identity against each gold plan.
- A period supplied by the evaluator for a query with no period is only checked to fall within the API's available range. The initial `need_period` response is recorded but not required for a pass.

## Scope

The retrieval runner will continue using the public v2.1 gold set and the in-process authenticated `/api/query` client with `execute=true`. `no_match` and clarification cases must not fetch data. Resolved cases may fetch statistical rows; chart and output generation remain outside this evaluation boundary.

For every resolved case, score each planned series independently using the full plan identity `(table_id, item_id, classifications, frequency, period_start, period_end)`. Compare runtime plans to gold plans with that identity. Attribute returned rows using their `TBL_ID`, `ITM_ID`, classification columns (`C1...`), and period; the runtime also adds `_FREQUENCY` and `_SOURCE_SERIES_ID`. Do not let rows for one series satisfy another series' checks.

For cases without an explicit period, require the first API response to be `need_period`. The follow-up request may inject the gold period for retrieval testing, but the report must identify that period as evaluator-supplied. Validate the applied period and returned period keys per series.

Use the frozen snapshot's series map as the baseline for the period keys and values that KOSIS actually returned. Verify the snapshot's gold and catalog hashes before scoring. The report must distinguish an application retrieval mismatch from a known snapshot coverage shortfall. In particular, a snapshot whose returned range is shorter than the gold plan must not be described as full requested-period coverage.

## Scoring and artifacts

The report will include counts for all 200 cases, the 140 resolved cases, all 294 expected series, fetched and missing series, unexpected series, per-series period coverage, and no-fetch compliance for the 60 cases whose gold status forbids retrieval. A case or series absent from the run output is a failure or explicit unevaluated state; it is never omitted from the denominator.

The run artifacts will record the dataset and catalog hashes, snapshot hash and reference date, evaluator source hash, execution policy, completion state, and whether the period was supplied by the evaluator. The command will return a nonzero status if the run is incomplete or if a required contract check fails.

## Tests

Add regression tests before implementation for:

1. Looking up the snapshot series through the actual nested schema.
2. Rejecting a wrong item or classification even when the table ID is correct.
3. Scoring multiple series independently and detecting one missing or short series.
4. Requiring the initial `need_period` state before injecting a period.
5. Rejecting applied periods outside the gold interval or returned period keys that do not cover the expected snapshot interval.
6. Keeping missing cases and series in the denominator.
7. Distinguishing known snapshot coverage shortfall from a runtime mismatch.

## Out of scope for this step

- Rewriting `score_execution_values.py` and the value comparison denominator.
- Changing `build_kosis_snapshot.py` or the live KOSIS verifier's exit policy.
- Changing discovery evaluation thresholds, repeat-sample gates, or timeout behavior.
- Editing gold queries or labels. The evaluation owner may revise those independently; this work consumes the validated public v2.1 dataset and its hashes.
- Calling live KOSIS, NCP, or other external services.

## Acceptance criteria

- Each expected series is scored against exactly one runtime series and its own returned rows.
- Each returned row's table, item, classification, period, and value can be attributed to a series without cross-series aggregation.
- Period-follow-up behavior is a scored contract.
- Missing evidence remains visible in the denominator.
- Tests demonstrate that the currently identified false-pass cases fail before the implementation and pass after it.
- The retrieval evaluator does not call output generation and reports any boundary violation.
- The evaluation remains explicitly a public development-set result, not a blind generalization score or human approval of the gold.

기업 제공 리소스를 우선으로 두면, 권장 구성은 **HyperCLOVA X로 질의를 해석하고, 임베딩 v2와 자체 표 카탈로그 검색으로 후보를 찾고, 필요할 때 리랭커로 재정렬한 뒤, KOSIS OpenAPI를 사용하는 MCP 도구로 표 메타정보를 확인하는 방식**입니다.

먼저 한 가지 구분이 필요합니다. 제공 목록에는 **KOSIS OpenAPI와 그 활용·MCP 설정 가이드**가 있습니다. 바로 연결해 쓸 실행 가능한 KOSIS MCP 서버까지 제공된 것으로 확인되지는 않으므로, 프로젝트에서 OpenAPI를 감싸는 MCP 서버를 구현하는 안을 권합니다.

## 단계별 권장 도구

| 단계 | 권장 도구 | 권장 구성 |
| --- | --- | --- |
| 자연어 질의 입력 | 서비스 입력 UI, 선택형 확인 UI | OpenCode Build의 확인 화면은 시제품 검증에 참고하고, 실제 서비스에서는 선택지·추천안·직접 입력을 제공하는 UI를 구현 |
| 의도·조건 추출 | **HCX-007** | 질의를 의도·지표·기간·비교 대상 JSON으로 추출. HCX-007은 Structured Outputs를 지원하므로 우선 검증 대상 |
| 통계 개념 정규화 | **Embedding v2 (`bge-m3`) + 검토된 별칭 사전** | 사용자 표현과 통계표 이름·분류 경로의 의미 유사도를 검색. `clir-emb-dolphin`, `clir-sts-dolphin`은 임베딩 비교 후보 |
| 모호성 점검·역질문 | **규칙 엔진 + HCX-007 또는 HCX-DASH-002** | 규칙이 확인 필요 여부를 정하고, LLM이 질문과 선택지를 작성. 사용자 응답은 서비스 UI에서 받음 |
| 데이터 전략·도구 계획 | **HCX-007 Function Calling + 코드 검증** | 허용된 도구 중 필요한 것을 계획하게 하고, 실행 전 도구명·인자·순서를 검증 |
| 통계표 탐색 | **로컬 카탈로그 검색 + NCP 리랭커 + KOSIS OpenAPI MCP 래퍼** | 로컬에서 349개 표를 먼저 검색하고, 필요 시 리랭커로 순서를 보정한 뒤 KOSIS 메타정보 API로 적합성 확인 |

NCP 공식 모델 표에 따르면
HCX-007은 Function Calling과 Structured Outputs를 지원합니다. 
HCX-005와 HCX-DASH-002는 Function Calling을 지원하고
HCX-003과 HCX-DASH-001은 지원하지 않습니다.
Structured Outputs는 HCX-007만 지원합니다. 

따라서 도구 실행계획의 핵심 비교 대상은 **HCX-007, HCX-005, HCX-DASH-002**로 제한하고, HCX-003·HCX-DASH-001은 간단한 추출 작업의 속도·비용 기준선으로 비교하는 편이 적절합니다.NCP CLOVA Studio 모델 기능표

### HyperCLOVA X 최대 5개 비교안

| 모델 | 비교할 역할 | 이 단계에서의 판단 |
| --- | --- | --- |
| HCX-007 | 복잡한 질의 해석, 모호성 판단, 계획 작성 | **주 추천 후보**. 구조화 출력과 도구 호출을 모두 지원 |
| HCX-005 | 질의 해석 및 도구 호출 | HCX-007 대비 품질·응답시간 비교 후보 |
| HCX-DASH-002 | 간단한 추출·질의 분류·질문 생성 | 빠른 처리 기준선 및 간단한 작업 후보 |
| HCX-003 | 간단한 슬롯 추출 | Function Calling 없이 구조화 결과를 만들 수 있는지 비교 |
| HCX-DASH-001 | 가장 가벼운 모델 기준선 | 최소 비용·응답시간 비교용. 핵심 계획 작성 모델로는 우선순위 낮음 |

이 표는 공식 기능 지원으로 역할을 나눈 것이며, 어느 모델의 질의 해석 품질이 실제로 가장 높은지는 골든셋으로 평가해야 합니다. 또 NCP 문서에는 HCX-007의 Function Calling과 Structured Outputs 등을 같은 요청에서 동시에 사용할 수 없다고 안내되어 있습니다. 따라서 **질의 추출은 구조화 출력 호출로, 도구 실행계획은 별도의 Function Calling 호출로 분리**하는 구성이 맞습니다.기능 조합 제한

## 임베딩·리랭커 비교안

임베딩은 에이전트가 아니라 검색 모델입니다. 349개 표에서는 우선 아래 4개 방식을 비교하면 충분합니다.

1. 별칭 사전 + 표 이름·분류 경로 키워드 검색만 사용
2. 키워드 검색 + `clir-emb-dolphin`
3. 키워드 검색 + `clir-sts-dolphin`
4. 키워드 검색 + **Embedding v2 (`bge-m3`)**

NCP 문서상 임베딩 모델은 같은 문장 쌍에도 서로 다른 유사도 점수를 내므로, 모델별 점수 임계값을 그대로 비교하면 안 됩니다. 동일 골든셋에서 **정답 표 Recall@5, MRR, Top-1 정확도**를 비교해야 합니다. Embedding v2는 BGE-M3 기반이며, 문서에서 새 임베딩 사용 시 시작점으로 권장합니다. 이에 따라 **Embedding v2를 주 후보**, 두 v1 모델을 비교 후보로 두겠습니다.NCP 임베딩 안내

리랭커는 최초 후보 검색기를 대신하지 않고 **검색된 후보의 순서를 보정하는 후처리 도구**로 사용합니다. 예를 들어 키워드·임베딩 검색으로 표 후보 상위 10~20개를 만든 뒤, 사용자 질의와 표 이름·경로를 리랭커에 넣어 순서를 비교합니다. 리랭커 API는 질의와 문서 목록을 받아 관련 문서를 선별하며, 최종 채택 여부는 정답 표의 순위가 실제로 개선되는지 확인해야 합니다.NCP 리랭커 API

## KOSIS 연계 권장안

- 표 목록 갱신: 제공 가이드의 `statisticsList.do`를 이용해 카탈로그 동기화
- 질의 시 후보 검색: 제공된 `hankook_tables.csv/json`을 인덱싱한 로컬 검색기로 빠르게 후보 선정
- 후보 검증: KOSIS 메타정보 OpenAPI를 부르는 프로젝트 MCP 도구로 항목·분류·주기·단위·수록 기간 확인
- 자료 조회: 표와 파라미터가 확정된 뒤에만 자료 조회 MCP 도구 호출
- 대안 경로: MCP 결과를 KOSIS OpenAPI 직접 호출 결과와 대조해 장애나 래퍼 오류를 진단

기업 가이드에는 통계목록·통계자료·메타정보 API가 각각 제공되는 정보가 구분되어 있습니다. 따라서 이를 `search_tables`, `get_table_metadata`, `query_data` 같은 명확한 MCP 도구로 감싸는 방향이 좋습니다. 통계표 탐색에서는 `search_tables`와 `get_table_metadata`까지만 사용하고, 수치 조회는 다음 단계로 넘깁니다.

NCP의 RAG Reasoning API는 문서 검색·근거 기반 답변을 위한 API이며, Function Calling 형식으로 복수 검색 함수를 선택할 수 있습니다.NCP RAG Reasoning 안내 다만 현재 설계는 Query Plan과 도구 순서를 명시적으로 평가해야 하므로, **초기 표 탐색 흐름의 주 오케스트레이터로 두기보다 후속 결과 설명 단계에서 비교하는 것**을 권합니다.

## 최종 비교 우선순위

1. **LLM:** HCX-007, HCX-005, HCX-DASH-002를 우선 비교하고, HCX-003·HCX-DASH-001은 간단 작업 기준선으로 측정
2. **검색:** 키워드 기준선, Embedding v2 하이브리드, 두 v1 임베딩 하이브리드를 비교
3. **리랭커:** 검색 전·후 정답 표 순위가 개선되는지 별도 측정
4. **데이터 접근:** 기업 KOSIS OpenAPI를 감싼 MCP 도구를 기본으로 두고, 직접 API 응답과 대조
5. **사용자 확인:** 선택형 서비스 UI를 구현하고, 질문 필요 판단과 답변 후 계획 해결률을 평가

따라서 지금의 **1차 권장 구성**은 `HCX-007 + 규칙 기반 검증 + 별칭 사전/키워드 검색 + Embedding v2 + 선택적 리랭커 + KOSIS OpenAPI MCP 래퍼`입니다. 최종 선택은 비용·속도뿐 아니라 골든셋의 슬롯 F1, 질문 판단률, 표 Recall@5, Top-1 정확도, MCP/API 일치율로 확정하면 됩니다.
